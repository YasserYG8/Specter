# Changelog

## Unreleased

### Breaking

- Specter now exits with status 1 when the target ended on its own (it exited, crashed or was killed, or the container stopped), and with status 0 only when you stopped it with Ctrl+C. It used to exit with 0 in both cases, so a script could not tell a crashed server from a normal stop.
- A bare number from 1 to 65535 is now a port and nothing else. It used to fall back to the process with that PID when nothing listened on the port, so `specter 3000` with your server down could attach `strace` to an unrelated process (and slow it) while only printing `Attaching to PID 3000 (systemd-journald)`. Now Specter prints "No process is listening on port 3000" with the active ports, exits with an error and attaches to nothing. If a process with that PID exists, the message ends with `Hint: PID 3000 exists (systemd-journald). To attach to it: specter --pid 3000`. To attach by PID, use the new `--pid` (`-p`) flag, for example `specter --pid 14280`. A number above 65535 cannot be a port, so `specter 70000` still attaches to PID 70000.
- `--level` with an unknown value is now an error that lists the valid levels. It used to be ignored, so `--level banana` showed every line. Aliases such as `warning`, `err` and `fatal` still work.

### Fixed

- Releases now publish Linux binaries only: `linux/amd64` and `linux/arm64` archives, `.deb` and `.rpm` packages, and `checksums.txt`. The macOS and Windows downloads are gone, because they could only print "needs Linux". CI still compiles for macOS and Windows to keep the code portable. On those systems, `specter <target>` now says what to do: on Windows, run it inside WSL2 (`wsl specter 3000`); on macOS, run your server and Specter in a Linux VM or a Docker container. The old message said "On Windows" even on macOS. `specter version`, `specter completion` and `--help` work everywhere.
- `--level` now works on common Python log formats. On a FastAPI server logging `2026-11-07 10:12:50,516 - TajweedPipeline - INFO - Starting pipeline`, `specter 8120 -l warn` still showed 64 of 67 lines, because Specter found no level in them and a line without a level is never hidden. It now reads the level of the logging cookbook format (`<time> - <logger> - INFO - ...`), of Celery (`[<time>: ERROR/ForkPoolWorker-1] ...`), and of lines like `2026-11-07 10:12:50,516 WARNING [app] ...`, where the timestamp has a space and a comma. These lines also start a new record, so a traceback after them stays grouped. A level word inside a message, such as `Processing item 3 - INFO - ...`, is not taken as the line's level, and formats that already worked (`INFO:app:...`, Gunicorn, loguru) are unchanged. Checked with a real Python process: `-l warn` showed 102 lines including 51 `INFO` before, and 51 lines with no `INFO` now.
- Specter now explains it when the target is already being traced. Linux allows one tracer per process, so a second Specter (or a plain `strace` or a debugger on the same process) used to fail with "Operation not permitted" and the advice to run `sudo`, which could not help. Now it stops before starting `strace` and says, for example, `PID 773 is already being traced by PID 844 (strace -f ...). Linux allows only one tracer per process. PID 844 was started by specter (PID 825).`, with the way out (stop the other Specter, or detach the other tracer). It never signals the other tracer. Workers that another process traces are left out, with one notice naming them and their tracers, so their missing output is explained. A tracer that appears between the check and the attach gets the same message. If `strace` cannot attach to the target itself while it keeps tracing workers, Specter now stops with an error instead of waiting silently.
- Specter now shows the output of Node.js servers started in a terminal. On a Next.js 16 dev server run with `pnpm run dev`, `specter 3000` showed none of the request lines (`GET /en/graphs 200 in 628ms`) and only the "Nothing captured yet" notice. Node writes to a terminal through a descriptor it opened again (fd 22 here), not through fd 1 or 2, so Specter skipped every line even though they reached the same terminal. Now a write through any other descriptor is shown when it leads to the same terminal, pipe or socket as the server's stdout or stderr. `/dev/null` is excluded, and writes to other places, such as a log file, are still ignored (the log file notice still works). Limit: those lines count as stdout, so `--stderr` hides them when stdout and stderr are the same terminal.
- Specter now says how the target ended. A normal exit used to print "Detached from PID N cleanly" (strace hid the exit line), and a target that wrote to a log file kept Specter waiting forever, with no message, until you pressed Ctrl+C. Now it prints `Target PID 617 exited with code 3.`, `Target PID 595 was killed by SIGKILL.` (with a hint about the kernel's out-of-memory killer and `dmesg | grep -i oom`), or `Container billing-api exited with code 137.`, and stops within about a second. "Detached cleanly" now means only that you interrupted. Only the target's own exit is reported, not that of a worker or helper.
- The `ptrace_scope` warning is no longer shown when Specter runs as root, since root can attach at scope 1 and 2. It is still shown at scope 3, which blocks everyone.
- Overlapping writes from threads and worker processes are no longer lost. With 4 worker processes writing 12,000 lines, Specter used to capture only a few hundred.
- `writev` calls are now captured.
- Lines up to 64 KB now arrive whole. A longer write keeps its line boundary and ends with `[specter: N more bytes not captured]`.
- A very long line of `strace` output no longer stops the capture.
- `--grep` now shows a whole stack trace when any of its lines matches. It used to show only the matching line and the lines after it, so `-g TypeError` on a Python traceback printed the last two lines without the header and frames, and a match on a frame lost the header. A trace with no matching line is still hidden. While `--grep` is set, Specter holds a trace until it ends (its last line, the next unrelated line, 200 ms of silence, or the end of the input), so lines from other processes can appear before it. A trace is matched on its first 1,000 lines. Without `--grep`, nothing is held.
- Lines that never reached the server's output are no longer shown. A Next.js dev server starts helper processes (such as `get-registry.js` and `telemetry/project-id.js`) whose output goes to a private pipe or `/dev/null`, but Specter printed it as if the server had logged it. Now a child process is shown only when its output goes to the same place as the server's own stdout or stderr. Workers that share the server's output are still shown, and so is everything the server writes itself, even when its stdout is `/dev/null`. If Specter cannot tell where a write went, it shows it.
- Every worker process of a server is now traced. Specter used to trace only the first 16 and printed no warning, so with 20 workers running before it attached, the last 4 lost all their logs. While attached, all workers are slowed, not just 16 of them.

### Added

- Notices on stderr when the target writes to its own log file, when nothing has been captured after 10 seconds, and when `--grep` is not a valid regular expression and is matched as literal text.
- Short flags `-l` (`--level`), `-g` (`--grep`), `-t` (`--tree`) and `-s` (`--source`). The README already listed them, but they were rejected with `unknown shorthand flag`.
